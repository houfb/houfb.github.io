# 测试目标：抽离原生标签内容
> 实测结论：
· Chrome原生HTML标签中，属性值中不能有 `>` 符及包裹所用的引号，其他字符任意，但要注意，这里的转义要用 `&amp;` 这种。  
· Chrome原生HTML标签的内容中可以出现任意字符，会原样输出，这包括 `\\ < > " ' =` 等这类敏感符，`<>` 只要不组成合法标签就行。 
· 在style块和script块的块内容中皆不能有闭标签，即使在字串、正则、注释中也不行，也即不能嵌套。  
· 原生HTML标签区的所有东西都不被marked编译处理。

# 测试目标：属性扩展
语法说明：`\{.cls #id [isn] [sex="man"]} | \{-- .cls #id [isn] [sex="man"]} | \{+ .cls #id [isn] [sex="man"]}`  
内置样式：.cc 文字居中 | .red 背景红色(相应的还有红黄绿...)  
 


#### 标题中的扩展样式可以在段落内的任意位置这样写{.cls #id [isn] [sex="man"]}，它可以被转义符消掉，如\{.cc}，它也可以连续写多个，比如再加一个{.iso}

- 列表的扩展样式{.cls #id [isn] [sex='man']}
 
普通段落的扩展样式：段落正{.cls #id [isn] [sex="man"]}文 | 段落正{.cls #id [isn] [sex='man']}文 | 段落正{.cls #id [isn] [sex=man]}文 | 额外格式={ }|{.cls}|{.cls#id}|{.cls #id}|{.cls #id [isn]}|{.cls #id [isn] [sex=man]}|{.cls #id [isn] [sex='man']}|{.cls #id [isn] [sex="man"]}
 
代码块中也可以插入属性扩展如{.cc}，但要注意，只能在用MD文本写的代码块才可以这样用，手写的原生HTML中的代码块不支持这个功能，这是为了保护原生HTML的兜底能力而故意设计。
 
- 属性扩展还可以沿着DOM父级节点链一路向左上去挂靠，用法如下：**这是一段加粗的文字，里边写了一个属性扩展{-- .red}，但却挂靠在ul标签身上**，这是个很有意思的扩展吧
 
- 属性扩展还可以尚着DOM开始标签一路向右去挂靠，用法如下：{+ .red}**加粗文字**，`\{...}`一路向右挂到第一个遇到的开始标签身上，这不分层级，只认开始标签。

```mermaid
sequenceDiagram
    participant Client as WebUpdater 客户端
    participant Server as WebUpdater 服务端
    participant Site   as 目标站点
     
    Client->>Client: 在配置文件中设置相关参数 
    Client->>Client: 监听目录变化，合并连续事件，触发更新流程<br/>（你可将监听目录设置为VS的发布目录）
    Client->>Client: 根据配置中的 TRaw 生成临时会话 AKey Ticket
   
    Note over Client,Server: 文件传输阶段
    Client->>Client: 扫出所有文件、计算文件MD等信息形成列表，<br/>剔除忽略项，得到总集 fileList
    Client->>Server: 调用CK接口，发送文件信息集（GCM加密）
    Server->>Client: 响应CK接口，返回服务端已有缓存的文件集
    Client->>Server: 对不足1MB的文件尝试批量合并上传（GCM加密）
    Client->>Server: 对其余文件走单文件上传，支持分片与断点续传（GCM加密） 
    Client->>Client: 校验，若有任何异常皆终止整个过程
     
    Note over Client,Site: 部署更新阶段
    Client->>Server: 调用UD接口，将文件集 fileList 发往服务端（GCM加密） 
    Server->>Server: 对数据进行解析与校验
    Server->>Server: 基础处理：<br/>标记站点已存在的无变更项<br/>若没配ExePath则尝试自动寻找首个exe文件
    Server->>Server: 备份站点文件

    Server->>Site: 不停机更新，仅将新增文件、常见格式的静态文件，直接尝试覆写到站点目录
    Server->>Site: 调用 StopUrl 通知站点关闭服务（站点须自行在回复完所有请求后再对此链作出200的响应）
    Server->>Site: 根据 ExePath ExeArgs 结束站点进程
    Server->>Site: 按列表从缓存刷入新文件
    Server->>Site: 启动站点进程
    Server->>Site: 根据 WellUrl 检查站点健康状态
    Server->>Server: 如果站点健康正常，则回复响应 SUCCESS，否则进入恢复阶段

    Note over Server,Site: 恢复阶段
    Server->>Site: 关闭站点服务，若有停机更新的文件，则需停机，否则不需要停机
    Server->>Site: 停止点站进程
    Server->>Site: 刷入备份文件
    Server->>Site: 启动站点进程
    Server->>Site: 检查站点健康状态
    Server->>Server: 如果站点健康正常，则回复响应 RECOVER，否则回复 FAIL 
    Server->>Client: 响应出执行结果：SUCCESS | RECOVER | FAIL

    Note over Client,Client: 报告阶段 
    Client->>Client: 收集执行过程中的重要信息，生成 MD 格式的表格，并写入单独的日志文件中
    Client->>Client: 若当前进程处于有UI模式，则自动打开这个日志文件，向开发者展示结果
    Client->>Client: 若此日志文件超过10分钟未被关闭，则自动关闭它。
   
```
